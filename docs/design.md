# Plan for a Retargetable In-Memory Assembler in OCaml

## 1. Objective

Build a standalone, retargetable assembler in OCaml for the architectures
supported by CompCert. It has a regular textual assembly frontend, but its staged
AST APIs also permit programmatic producers to bypass parsing. Its primary output
is a linked executable image in memory, not an object file.

The production library is pure OCaml and browser-embeddable through both
js_of_ocaml and Melange. It contains no C source or foreign stubs and has no
direct or transitive library dependency that requires C code. C programs and
target runtime sources may appear as compiler-input fixtures, but are data tested
by the assembler rather than implementation code linked into it.

The initial compatibility contract is deliberately external to CompCert:

1. Run an unmodified CompCert with `ccomp -S`.
2. Parse and assemble the emitted textual assembly.
3. Combine one or more assembly inputs with an internal linker.
4. Materialize executable and data segments in memory.
5. Compare encodings and behavior against trusted GNU or LLVM tools.

Direct consumption of CompCert's internal `Asm.program` representation is a much
later integration step. It must reuse the same semantic assembler and linker
pipeline through a public AST boundary rather than becoming the initial
architecture of the project.

## 2. Scope

### 2.1 Required in the initial project

- Textual assembly input, including ordinary handwritten assembly and `.s` files
  emitted by unmodified CompCert.
- Multiple input files in one assembly/link operation.
- Target-specific instruction parsing, validation, pseudo-instruction lowering,
  and encoding.
- Public source, normalized, and lowered ASTs with independent parsing,
  simplification, lowering, validation, and image-building passes.
- Programmatic construction of normalized or lowered ASTs without textual
  round-tripping.
- Sections, alignment, initialized data, zero-filled storage, symbol definitions,
  and symbolic expressions needed to construct an executable image.
- Local, global, weak, common, and undefined linker-visible symbols.
- Internal fixups, layout, symbol resolution, branch relaxation, and range checks.
- An in-memory result containing executable, read-only, writable, and zero-filled
  segments.
- Fixed-address and caller-selected virtual-address binding modes.
- Clear diagnostics with text locations or programmatic producer origins.
- Expect-based tests covering each observable pipeline stage.
- A small target-aware disassembler for diagnostics, encoding inspection, and
  round-trip tests.
- Differential validation against the assembly generated by an unmodified
  CompCert and against existing assemblers.
- A pure-OCaml production dependency closure that compiles with native OCaml,
  js_of_ocaml, and Melange, with identical assembler/linker results on all three.
- Browser-facing APIs that accept and return in-memory values without requiring a
  filesystem, subprocess, environment variables, native pointers, or Unix APIs.

### 2.2 Explicit non-goals for now

- ELF, Mach-O, COFF, or any other object-file output.
- Static-library archive formats.
- Dynamic linking, shared libraries, PLT/GOT construction, symbol interposition,
  or `dlopen`-style behavior.
- Debugger information, source-to-address mappings, DWARF, CodeView, STABS, or
  debugger-oriented symbol tables.
- Unwind information and exception-frame construction.
- Preserving `.file`, `.loc`, `.cfi_*`, or similar metadata in the output.
- Formal verification of the complete assembler in the first implementation.
- Direct modification of CompCert's compilation pipeline in early milestones.
- C stubs, foreign-function bindings, C-backed OCaml libraries, or native-only
  dependencies in any production package.
- Executing x86, ARM, or AArch64 machine code inside a browser. Browser embedding
  covers parsing, assembly, internal linking, image materialization, and
  inspection; execution remains an out-of-process validation concern.

The exclusion of debugger symbols does not remove semantic symbols. Labels,
global definitions, weak/common definitions, undefined references, exports, and
the entry symbol are essential inputs to internal linking and must remain in the
core data model.

Debug and unwind directives emitted by CompCert should be handled through a
documented compatibility policy:

- Known metadata-only directives may be parsed and discarded.
- Their arguments should still be lexically and structurally consumed so that a
  malformed directive does not corrupt parsing of the following statement.
- Unknown directives must produce a diagnostic unless a target profile explicitly
  classifies them as safe metadata-only directives.
- No debug or unwind fragment should enter the semantic module or linked image.

## 3. Design principles

### 3.1 Retarget by target profile, not only by ISA

The retargeting unit is:

```text
ISA x ABI x textual dialect x endianness x feature set
```

This is necessary even without object-file output. CompCert's assembly syntax,
section directives, symbol spellings, comment syntax, and available instructions
vary across platforms and configurations.

The architecture-independent engine must not contain a central variant listing
every register, opcode, operand, or relocation form for every ISA. Those types and
operations belong to target modules.

### 3.2 Keep syntax, instruction semantics, and layout separate

The pipeline should have distinct, public boundaries:

```text
text source
  -> parser
  -> source AST
  -> simplification and normalization
  -> normalized semantic AST
  -> target lowering
  -> lowered module AST: sections, fragments, symbols, fixups

one or more lowered modules
  -> symbol resolution, layout, relaxation, encoding, final fixups
  -> linked logical image
  -> address-bound in-memory image
```

Parsing is only one way to enter the pipeline. A CompCert adapter or another code
generator may construct the source AST, normalized AST, or lowered module AST
directly. It must not print assembly text merely so the assembler can parse it
again.

Each arrow is an independently callable and testable pass with explicit input and
output types. Parsing does not fold constants or select encodings; simplification
does not perform layout; lowering does not resolve symbols across modules; and the
link/image step does not reinterpret textual syntax. This separation permits new
frontends, syntactic dialects, instruction sets, and loading policies to evolve
independently.

### 3.3 Treat external tools as test oracles, not runtime dependencies

GNU `as`, LLVM `llvm-mc`, object readers, and disassemblers may be used by tests to
obtain reference encodings. Production assembly and linking must not invoke an
external assembler or linker.

The repository devcontainer is the baseline oracle environment. It provides one
prefixed GNU toolchain for every initial profile:

| Target profile | CompCert installation | GNU oracle prefix | QEMU user runner |
|---|---|---|---|
| x86-32 Linux | `.cross-smoke-work/install/x86_32/bin/ccomp` | `i686-linux-gnu-` | `qemu-i386` |
| x86-64 Linux | `.cross-smoke-work/install/x86_64/bin/ccomp` | `x86_64-linux-gnu-` | `qemu-x86_64` |
| ARMv7-A Linux, hard-float, ARM mode | `.cross-smoke-work/install/arm/bin/ccomp -marm` | `arm-linux-gnueabihf-` | `qemu-arm` |
| AArch64 Linux | `.cross-smoke-work/install/aarch64/bin/ccomp` | `aarch64-linux-gnu-` | `qemu-aarch64` |

`tools/compcert-cross-smoke.sh all` creates those four isolated installations and
validates the complete C-to-executable path. Tests should call the prefixed
`as`, `objcopy`, `objdump`, and `readelf` directly when establishing assembler
ground truth; using only `gcc -c` would obscure which oracle stage produced a
result. The compiler driver remains useful as a second acceptance check because
it uses the exact assembler options recorded by CompCert.

Oracle executables and their `--version` output are part of test provenance.
Reference `.o`, extracted section bytes, symbol/relocation dumps, and disassembly
are diagnostic test artifacts only. They never enter the production assembler or
linker pipeline.

### 3.4 Develop four architecture slices in parallel

The initial targets are x86-32, x86-64, ARM, and AArch64. The project must not
complete one target before exposing the common design to the others. That would
risk making fixed-width encodings, a particular register model, or one style of
address expression accidental assumptions of the shared core.

Development proceeds by semantic capability slices. For example, the first slice
supports only what CompCert emits for a freestanding function returning a
constant, but supports that slice on all four targets. Later slices add arguments,
arithmetic, globals, control flow, direct calls, data, and multi-file references in
parallel.

The four targets deliberately stress different parts of the design:

| Target | Early design pressure |
|---|---|
| x86-32 | Variable-length encodings, prefixes, ModR/M and SIB, 32-bit runtime helpers |
| x86-64 | REX selection, RIP-relative addressing, several equivalent encodings |
| ARM | Condition fields, flexible operands, literal/address materialization, range handling |
| AArch64 | Fixed-width encoding, page-relative addresses, split immediates and fixups |

Parallel does not require identical instruction counts or equal implementation
effort in every iteration. It requires every new architecture-independent
abstraction to be exercised by a real expect test on all four targets before it is
treated as stable.

### 3.5 Make observable behavior testable by construction

Every pipeline boundary should have a deterministic textual rendering intended
for expect tests: tokens/statements, matched instructions, fragments, symbols,
fixups, layout, image bytes, disassembly, diagnostics, and execution result. These
renderings are a supported development interface, although not necessarily a
stable public file format.

Addresses, generated local names, and map iteration order must be normalized so
that expect output is reproducible. When exact addresses matter, the test uses an
explicit fixed layout.

### 3.6 Enforce one-way dependencies between machinery and targets

The generic EDSL, codec interpreters, assembler engine, linker, and image model
must be separate compilation units from all architecture descriptions. Dependency
direction is one way:

```text
generic foundations
  <- generic codec/EDSL and generators
  <- generic assembler/linker/address-binding machinery
  <- target-family combinators
  <- concrete target profiles
  <- driver registry and executable
```

Generic packages must not import x86, ARM, AArch64, PowerPC, or RISC-V modules and
must not contain a `match target with ...` dispatch. When generic machinery needs
target behavior, it receives an abstract operation through a module signature,
functor argument, or typed description value.

Architecture-specific reusable concepts remain outside the generic EDSL. For
example, x86 prefix/ModR/M/SIB combinators belong to an x86-family library; ARM
rotated/split-immediate helpers belong to an ARM target library. The generic codec
provides only concepts such as sequencing, alternatives, fields, constraints,
partial isomorphisms, context parameters, and diagnostics.

Do not move a target helper into the generic layer merely to remove duplication.
Promote an abstraction only when it has target-independent semantics and either
appears in structurally different architectures or is a fundamental codec/layout
operation. This prevents the first implemented target from silently defining the
generic model.

### 3.7 Keep the production closure pure OCaml and browser-portable

Every production library, including concrete targets and the runtime target
registry, must compile without foreign stubs. This rule is transitive: a package
is not acceptable merely because this repository contains no C if one of its
dependencies links C code. In particular, do not use a GMP/C-backed arbitrary-
precision package, `ctypes`, native memory-mapping bindings, or a package that
silently selects a C accelerator.

The portable closure must also avoid native host facilities in its APIs and
implementation:

- No `Unix`, `Dynlink`, process creation, signals, filesystem access, environment
  lookup, native threads/domains, or wall-clock dependence.
- No native pointers or bigarrays as canonical storage. Use a project-owned byte
  cursor/buffer abstraction implemented in pure OCaml; thin JavaScript adapters
  may copy to or from `ArrayBuffer`/typed arrays at the browser boundary.
- No reliance on JavaScript `Number` for target addresses or assembler integer
  expressions. Use checked fixed-width types for target fields and a pure-OCaml
  arbitrary-precision representation for parsing and symbolic arithmetic.
- No global mutable registry initialized through native side effects. Target
  selection is an ordinary pure OCaml value passed to or returned by the public
  API.
- No exception or diagnostic text that depends on host paths, locale, process
  state, or nondeterministic iteration order.
- No error-provenance text - an err-trace origin, stack, event or observation -
  in an expect or cram baseline. Foundation.Err_policy keeps automatic stack
  capture off for the same reason; see asm/docs/errors.md §3.

Host tools are deliberately outside this closure. Shell/CI harnesses may run
CompCert, GNU binutils, QEMU, Node.js, or a browser runner and feed their artifacts
to the portable library. These executables are development or validation oracles,
not linked dependencies. Any optional native executor is a separate process with
a serialized protocol; the embeddable library must neither link it nor know how
it is implemented.

CI must enforce this boundary rather than relying on convention: audit the full
production dependency graph for foreign stubs, reject `foreign_stubs` and C
objects in build metadata, compile the same public library with js_of_ocaml and
Melange, and run a deterministic smoke corpus through both generated JavaScript
artifacts.

## 4. Frontends and staged ASTs

### 4.1 Public phase API

The error type below is the M0 sketch. It is now a typed domain per module,
wrapped by err-trace, with `Diagnostic.t` produced only at the reporting
boundary; see asm/docs/errors.md. The staging and the entry points are
unchanged.

```ocaml
module type PIPELINE = sig
  module Source_ast : sig type module_ end
  module Normalized_ast : sig type module_ end
  module Lowered_ast : sig type module_ end

  val parse :
    source_unit ->
    (Source_ast.module_, Diagnostic.t list) result

  val simplify :
    Source_ast.module_ ->
    (Normalized_ast.module_, Diagnostic.t list) result

  val lower :
    Normalized_ast.module_ ->
    (Lowered_ast.module_, Diagnostic.t list) result

  val build_image :
    layout_policy ->
    Lowered_ast.module_ list ->
    (logical_image, Diagnostic.t list) result
end
```

Convenience functions such as `assemble_text` may compose these passes, but the
individual entry points remain public. Each AST type has a validator and safe
constructors so a direct producer cannot silently violate invariants that the
textual path normally establishes.

These entry points consume explicit strings, byte buffers, AST values, target
profiles, and layout policies only. File loading, command-line parsing, tool
invocation, and environment discovery are adapters outside `PIPELINE`; a browser
caller can invoke every phase without emulating a POSIX host.

Origins used in diagnostics must not assume text input:

```ocaml
type origin =
  | Text of Span.t
  | Producer of { tool : string; item : string option }
  | Synthesized of { pass : string; parent : origin option }
```

This is diagnostic provenance, not debugger/source-map information, and is not
included in the generated image.

### 4.2 Source AST

The public result of parsing is a complete source AST, not tokens or operand token
slices. It represents labels, assignments, directives, parsed expressions, and
target-specific surface instructions while preserving source spelling and origin
where useful for diagnostics.

The source AST may still contain:

- Assembly aliases and pseudo-instructions.
- Numeric local-label references.
- Directive variants and syntactic sugar.
- Expressions containing symbols and the current-location operator.
- Values that have not yet been range checked against an encoding.

Lexer tokens and the shallow common statement representation described below are
private frontend intermediates used to build this AST.

### 4.3 Normalized semantic AST

The independent `simplify` pass converts the source AST to a normalized semantic
AST. Its responsibilities include:

- Constant folding with arbitrary-precision integers.
- Algebraic simplification and canonical expression forms.
- Directive desugaring and normalization.
- Resolution of numeric local labels into unambiguous internal names.
- Target operand validation and conversion to canonical semantic operands.
- Alias normalization and local pseudo expansion that is independent of layout.
- Removal of metadata-only directives.

Only absolute subexpressions may be folded early. Expressions involving symbols,
the current location, section placement, or PC-relative bases remain symbolic
until the environment required to evaluate them exists. Overflow/range checks are
performed when converting an arbitrary-precision value to a specific field, not
by allowing host-integer overflow during folding.

The normalized AST has no dependence on textual tokenization. It is the preferred
entry point for a compiler that wants the assembler to retain responsibility for
instruction-form selection, pseudo lowering, fixups, and layout.

### 4.4 Lowered module AST

The independent `lower` pass turns normalized semantic operations into the
internal module form needed by image construction:

- Logical sections and permissions.
- Data, alignment, zero-fill, and relaxable instruction fragments.
- Module-local and externally visible symbol definitions.
- Symbolic fixups with target-specific kinds.
- Exact or alternative encoding forms where selection is already possible.
- Remaining target pseudos whose expansion legitimately depends on layout.

The lowered AST contains no final addresses and performs no cross-module symbol
resolution. It is the preferred entry point for a lower-level code generator or
JIT frontend that already knows target instructions and section placement but
wants this project to perform linking, relaxation, encoding, and image loading.

`build_image` accepts several lowered modules, validates their target-profile
compatibility, resolves symbols, lays them out, chooses remaining alternatives,
encodes bytes, applies fixups, and returns the linked image.

### 4.5 Direct AST producers

Supported frontend paths are therefore:

```text
assembly text -> Source AST -> Normalized AST -> Lowered AST -> image
external Source AST -------> Normalized AST -> Lowered AST -> image
CompCert/semantic producer -----------------> Normalized AST -> ...
lower-level code generator ---------------------------------> Lowered AST -> image
```

Direct construction must use versioned public interfaces or smart constructors
and must run the phase validator at the entry boundary. Skipping text parsing must
not skip semantic validation, target-feature checks, symbol invariants, or fixup
range checks.

The direct CompCert adapter is still a late milestone, but the AST boundaries are
designed from the beginning so that integration is addition of a frontend rather
than replacement of the assembler pipeline.

### 4.6 Dialect-aware lexer

The lexer produces tokens with exact source spans. Its configuration is supplied
by the target profile and covers:

- Comment introducers and statement separators.
- Identifier characters and symbol naming rules.
- Register and immediate sigils such as `%`, `$`, and `#`.
- Integer bases, character constants, string escapes, and floating constants.
- Numeric local labels such as `1:`, `1b`, and `1f`.
- Target expression operators and modifier spellings.

This is target-configured because `#` can be an immediate marker in one dialect
and a comment marker in another. A single hard-coded assembly lexer would produce
subtle cross-target failures.

### 4.7 Common parser representation

The common parser recognizes labels, assignments, directives, and instruction
lines but does not attempt to understand every target operand. This is an
intermediate concrete-syntax representation, not the public source AST:

```ocaml
type statement =
  | Instruction of {
      mnemonic : string;
      operands : token_slice list;
      span : Span.t;
    }
  | Directive of {
      name : string;
      arguments : token_slice;
      span : Span.t;
    }
  | Assignment of symbol * expr
  | Empty

type line = {
  labels : label list;
  statement : statement;
  span : Span.t;
}
```

Operands remain token slices only until delegated to a target parser that completes
the source AST. This avoids a false universal grammar for x86 addressing, ARM
register lists, AArch64
shift/extend operands, and RISC-V or PowerPC address modifiers.

Menhir is suitable for the stable common grammar and expressions. Small
hand-written token-cursor parsers are preferable for target operands. Individual
instruction forms must not become Menhir productions.

### 4.8 Common expression language

Expressions are shared by data directives, symbol assignments, alignment, and
instruction operands:

```ocaml
type expr =
  | Const of Z.t
  | Symbol of symbol
  | Current_location
  | Add of expr * expr
  | Sub of expr * expr
  | Mul of expr * expr
  | Shift of shift_op * expr * expr
  | Bitwise of bit_op * expr * expr
  | Modifier of target_modifier * expr
```

The target interprets `Modifier`, allowing representations such as RISC-V
`%pcrel_hi`, PowerPC `@ha`, or AArch64 page-address forms without embedding their
semantics in the common parser.

Expression evaluation must distinguish:

- Absolute values known immediately.
- Section-relative or symbol-relative values resolved during layout.
- Values requiring a target fixup at final load address.
- Invalid expressions that cannot be represented by the requested encoding.

### 4.9 Declarative instruction forms

Instruction descriptions should be declarative and generate matcher, encoder,
decoder, printer, and test tables. Assembly syntax and binary encoding are not a
one-to-one relation, so the model must distinguish three levels:

```text
textual syntax
  -> canonical semantic instruction
  -> exact encoding form
  -> bytes
```

The reverse path decodes bytes to an exact form, recovers the semantic
instruction, and only then prints canonical syntax. This separation represents:

- Several textual aliases for one semantic instruction.
- Pseudo-instructions that lower to several real instructions.
- Several legal binary forms for the same semantic instruction.
- Short/long alternatives selected by layout and relaxation.
- Exact form identity needed by the diagnostic disassembler.

Each syntax form describes:

- Mnemonic and aliases.
- Operand count and operand classes.
- Required target features or execution mode.

Each encoding form describes:

- Encoding fields and constant bits.
- Immediate ranges and alignment constraints.
- Symbolic fixups created by operands.
- Alternative encodings used by relaxation.
- Selection and decode priority.
- A stable diagnostic form identifier.
- The mapping to and from a semantic instruction.

The parser first turns operand slices into target surface-operand AST values. The
simplifier validates and canonicalizes them into semantic instructions. Lowering
then selects an exact or relaxable set of encoding forms. Alias and
pseudo-instruction handling is therefore testable independently of byte emission.

#### 4.9.1 Typed bidirectional codec representation

The initial description mechanism should be a typed OCaml embedded DSL whose
values are inspectable codec trees. Descriptions must not be arbitrary encoding
functions: an opaque function cannot be inverted or inspected to generate a
decoder, conflict checker, printer, or tests.

A simplified codec interface is:

```ocaml
type 'a codec

val constant : width:int -> Z.t -> unit codec
val field : width:int -> signedness -> Z.t codec
val both : 'a codec -> 'b codec -> ('a * 'b) codec
val partial_iso :
  encode:('a -> 'b option) ->
  decode:('b -> 'a option) ->
  'b codec ->
  'a codec
```

The codec value is interpreted several ways:

- Encode typed fields to bytes and fixup placeholders.
- Decode bytes to typed fields and an exact form identifier.
- Build efficient decode tables or tries.
- Check fixed-bit overlaps, unreachable forms, and ambiguous priorities.
- Generate operand boundary and encoder/decoder round-trip cases.
- Produce diagnostic descriptions of field placement.

The generic codec primitives and target-family combinators together must
eventually express:

- Fixed and variable instruction widths and target endianness.
- Constant, signed, unsigned, scaled, split, and reserved fields.
- Register encoding maps.
- Optional and conditionally present bytes or fields.
- Conditional sequencing suitable for prefix and opcode-map selection.
- Composable target-family subformats such as x86 ModR/M, SIB, displacement, and
  immediate components.
- Architecture decode context and feature predicates.
- Explicitly ordered overlaps and aliases.
- Fixup field transformations and PC-relative bases.
- Alternative encodings with size/cost policy.

Fixed-width formats can use direct bit-field combinators. x86 should use reusable
family combinators for prefixes, opcode maps, ModR/M, and SIB rather than forcing
those concepts into a flat 32-bit-style pattern or adding x86-named operations to
the generic EDSL.

Some irregular encodings will require handwritten, target-local escape hatches.
Every escape hatch must provide both encoding and decoding where applicable and
must have focused expect and independent differential tests.

#### 4.9.2 Evolution to an external instruction language

The codec abstractions should first be exercised on x86-32, x86-64, ARM, and
AArch64. Once those four targets stabilize the concepts, a compact `.isa` language
can elaborate into the same typed internal codec representation and generate
ordinary `.ml`/`.mli` tables.

A dedicated syntax or S-expression notation is preferable to JSON or YAML because
instruction descriptions need reusable format definitions, bit ranges,
expressions, overlap groups, typed operands, and precise source diagnostics.

The eventual generator should emit:

- Semantic opcode and exact form identifiers.
- Operand matcher tables.
- Encoder and decoder tables.
- Canonical and diagnostic printers.
- Form feature/range metadata.
- Static ambiguity and reachability reports.
- Automatically derived boundary and round-trip tests.

This follows the useful parts of LLVM MC and TableGen while retaining a more
explicit relation between syntax, semantics, and exact encodings. LLVM's object
streamers and object writers are not part of this design.

### 4.10 Assembly-language expansion

The first milestone accepts already preprocessed `.s` files. CompCert runtime
`.S` files can be passed through the platform C preprocessor by the external
fixture-generation harness before being supplied to the assembler. The production
library never spawns or links a C preprocessor; browser callers either provide
preprocessed text or use assembly-language expansion implemented in pure OCaml.

General assembler language features are staged separately from instruction
parsing:

- Initial: labels, assignments, data/section directives, and instructions.
- Later: `.include`, conditional assembly, repetition, user macros, and target
  macro conventions.

Syntactic macro expansion belongs inside the textual frontend and should produce
the same source-AST nodes as ordinary parsed text while retaining an expansion
trace for diagnostics. It must not be mixed into semantic simplification, target
encoding, or the APIs used by direct AST producers.

## 5. OCaml type and module structure

### 5.1 Target interface and functors

The architecture-independent assembler should depend on an interface similar to:

```ocaml
module type TARGET = sig
  type register
  type surface_operand
  type surface_instruction
  type opcode
  type instruction
  type lowered_instruction
  type encoding_form
  type feature
  type fixup_kind
  type form_id
  type decode_context
  type target_state

  val lexical_profile : Lexical_profile.t
  val parse_surface_operand :
    token_slice -> (surface_operand, Diagnostic.t) result
  val make_surface_instruction :
    mnemonic:string ->
    surface_operand list ->
    (surface_instruction, Diagnostic.t) result
  val simplify_instruction :
    features:feature list ->
    surface_instruction ->
    (instruction, Diagnostic.t) result
  val lower_instruction :
    target_state -> instruction -> lowered_instruction list
  val encoding_alternatives :
    lowered_instruction -> encoding_form list
  val encode_form : encoding_form -> encoded_fragment
  val decode :
    decode_context ->
    bytes_view ->
    (instruction * form_id * int, Diagnostic.t) result
  val evaluate_fixup :
    fixup_kind -> place:address -> target:address ->
    (encoded_value, Diagnostic.t) result
  val nop_bytes : length:int -> (bytes, Diagnostic.t) result
  val handle_directive : directive -> target_state -> directive_result
end
```

Target state covers features and modes such as ARM/Thumb or RISC-V options. It
must not contain global linker state.

The common implementation is constructed by functors:

```ocaml
module Make_assembler (T : TARGET) = struct
  module Parser = Parser.Make(T)
  module Encoder = Encoder.Make(T)
  module Disassembler = Disassembler.Make(T)
  module Layout = Layout.Make(T)
end
```

Functors provide the main retargetability boundary: target-specific types remain
abstract, while source-AST construction, simplification orchestration, fragment
construction, symbol processing, layout iteration, image creation, diagnostics,
and test rendering are shared.

Family functors may share genuine structure, for example:

```ocaml
module X86_32 = X86.Make(X86_mode_32)
module X86_64 = X86.Make(X86_mode_64)
```

The family parameter must expose real differences such as register availability,
default operand/address size, prefix and REX behavior, RIP-relative addressing,
and enabled forms. ARM and AArch64 should not be forced into one family functor.

The CLI chooses a target at runtime, after functor application. Each completed
target driver should therefore be hidden behind a uniform first-class module that
exposes only architecture-independent requests and results:

```ocaml
module type DRIVER = sig
  val name : string
  val assemble : request -> (image, Diagnostic.t list) result
  val disassemble : disasm_request -> disasm_result
end
```

This prevents existential target types from spreading through the command-line
driver and internal linker. Avoid many layers of tiny functors: use one obvious
top-level target functor and a small number of mechanism/family functors.

Programmatic AST producers use the statically selected target module rather than
the erased CLI `DRIVER` interface. This preserves the target-specific AST types
and lets OCaml check that, for example, an ARM normalized AST is not passed to an
x86 lowering pipeline. The outer runtime registry is for textual CLI requests and
other architecture-erased operations.

CompCert's existing `Asmexpandaux.Branch_relaxation` functor is a local precedent:
it shares the layout iteration while a target supplies instruction size, range
testing, and expansion.

### 5.2 GADTs and typed instruction schemas

GADTs are useful inside a target and the codec DSL where matching a value should
recover type information. Suitable invariants include:

- Register width/class agrees with an operand schema.
- A branch form receives a branch target rather than arbitrary memory.
- An operand tuple has the arity and types required by its encoding form.
- A decoded field tuple can construct only the matching semantic instruction.

For example:

```ocaml
type w8
type w16
type w32
type w64

type _ width =
  | W8 : w8 width
  | W16 : w16 width
  | W32 : w32 width
  | W64 : w64 width

type _ operand_kind =
  | Gpr : 'w width * register_class -> 'w register operand_kind
  | Imm : signedness * int -> Z.t operand_kind
  | Mem : address_class -> memory_operand operand_kind
  | Target : branch_class -> expr operand_kind

type _ operands =
  | ONil : unit operands
  | OCons : 'a operand_kind * 'b operands -> ('a * 'b) operands

type form =
  | Form : {
      id : form_id;
      operands : 'ops operands;
      encoding : 'ops codec;
    } -> form
```

The matcher validates untyped textual operands once and produces the typed tuple
consumed by the codec. The encoder then does not repeat width, class, and arity
checks.

GADTs should not define one project-wide constructor for every instruction on
every architecture. That would produce huge generated types, awkward existential
packaging, difficult diagnostics, and pressure to expose target details in common
code. Prefer:

- Abstract target instruction types at functor boundaries.
- GADTs for operand schemas, widths, typed fields, and codec combinators.
- Phantom types for simple distinctions that do not need type-refining pattern
  matching.
- Runtime validators for irregular constraints that gain little from type-level
  encoding.

### 5.3 Package boundaries

A suitable source layout is:

```text
lib/foundation/       spans, diagnostics, integers, byte cursors
lib/codec/            generic typed EDSL and encoder/decoder interpreters
lib/isa_gen/          generic validation and optional source generator
lib/asm_core/         source/normalized/lowered AST containers and common passes
lib/image/            symbols, linker, layout, fixups, logical image, address binding
lib/target_intf/      module signatures only
targets/x86_family/   prefixes, opcode maps, ModR/M, SIB, x86 shared forms
targets/x86_32/       concrete syntax, registers, forms, fixups, profile
targets/x86_64/       concrete syntax, registers, forms, fixups, profile
targets/arm/           ARM-specific descriptions and helpers
targets/aarch64/       AArch64-specific descriptions and helpers
driver/                portable functor applications and target registry
browser/               thin js_of_ocaml and Melange API adapters
tool/                  optional host CLI; never a library dependency
test/oracle/           shell/CI orchestration for CompCert, GNU tools, and QEMU
```

The exact directory names may change, but the dependency graph must not. In
particular:

- `lib/codec` is compilable and testable without any real architecture.
- Generic EDSL values contain no global mutable target registration.
- Target descriptions may build values using the EDSL but cannot change its
  semantics.
- Generated code conforms to target interfaces and does not generate changes
  inside generic packages.
- The target registry exists only at the outer composition layer.
- Handwritten escape hatches live in the target or target-family package that
  needs them.
- Every library from `lib/` through `browser/` has only pure-OCaml transitive
  dependencies and compiles under both JavaScript backends.
- `tool/` and `test/oracle/` may perform host I/O or invoke external executables,
  but no production or browser package may depend on them.

Do not select an arbitrary-precision, parser, property-test, or serialization
library until its transitive build has been audited for C stubs. If no suitable
pure-OCaml arbitrary-precision implementation meets the backend matrix, implement
the minimal signed big-integer operations required by assembly expressions in
`lib/foundation` and test them against external vectors. Zarith/GMP is not an
acceptable production dependency under this constraint.

Generic codec tests should use one or more small synthetic ISAs to test field
composition, alternatives, ambiguity rejection, partial isomorphisms, variable
length, endianness, and failure reporting. Real-architecture expect tests then
validate that the abstraction is sufficient without becoming dependencies of the
generic test suite.

When a target exposes a missing capability, first implement or prototype it in
the target-family layer. Promote only the smallest semantic primitive needed by
the generic EDSL, add a synthetic-ISA test for that primitive, and keep the
architecture-shaped convenience combinator in the target package. Design reviews
should reject generic APIs whose names, types, or control flow reveal one target's
encoding vocabulary.

## 6. Diagnostic disassembler

A small disassembler is part of the development and debugging toolset. It is not
intended initially to compete with a full debugger or general-purpose
disassembler. Its required domain is the set of instruction forms implemented by
the assembler, plus graceful handling of unknown byte sequences.

The disassembler serves four concrete purposes:

- Make expect-test failures readable by showing bytes next to decoded
  instructions.
- Identify which encoding form the assembler selected when several forms have the
  same assembly-level meaning.
- Check encoder/decoder round trips and instruction boundaries.
- Compare canonical instruction streams when exact byte equality is not required
  because multiple encodings are valid.

Instruction descriptions should generate as much of the decode tables as
practical, but targets may supply custom decoding logic where an encoding family
is irregular. A decoded instruction should retain:

```ocaml
type 'instruction decoded = {
  address : address;
  bytes : bytes;
  instruction : 'instruction;
  form_id : form_id;
}
```

`form_id` is diagnostic information naming the precise encoding alternative; it
is not source-level debug metadata.

Two print modes are useful:

- Canonical mode prints normalized assembly suitable for semantic comparison and
  ordinary round-trip tests.
- Diagnostic mode also prints addresses, raw bytes, instruction length, and form
  identifier, making ambiguous or unexpectedly selected encodings visible.

The relevant round-trip properties are:

```text
decode(encode(instruction)) = same semantic instruction
encode_exact(decode(bytes).form_id) = bytes
```

Canonical reassembly is not always required to reproduce the original bytes,
because a canonical printer may intentionally choose one of several legal
encodings. The exact-form property covers that case.

The internal disassembler cannot independently prove the encoder correct if both
are generated from the same erroneous description. GNU and LLVM assemblers and
disassemblers therefore remain independent differential oracles.

Encoder and decoder generation should share the typed codec representation, not
duplicate field positions in two tables. Their generated implementations should
still be tested separately: specification errors can be self-consistent in both
directions, while generator bugs can affect only one interpreter of the codec.

## 7. Lowered fragments and assembler modules

The lowering pass, not the parser, converts normalized semantic AST statements
into fragments. Important fragment kinds include:

- Encoded or relaxable instruction.
- Literal byte sequence.
- Integer or floating data with possible fixup.
- String data.
- Alignment request with a target-selected fill policy.
- Zero-filled storage.
- Symbol definition or alias.
- Section boundary/state change.

A lowered assembler module represents one input unit, whether parsed from text or
constructed directly, and contains:

- Logical sections and section attributes relevant to memory permissions.
- Ordered fragments in each section.
- A private namespace for local symbols.
- Global, weak, common, and undefined symbol declarations.
- Fixups with target kind, expression, diagnostic origin, and patch location.

This representation has some of the same information as an object file because
the internal linker needs it, but it is never serialized as an object file.

Debug-source records, line tables, CFI records, and debugger symbol attributes are
excluded from the assembler module.

## 8. Internal linker and layout/image engine

The image builder consumes all validated lowered modules together. It must not
require the user to choose an arbitrary file ordering for symbol resolution and
does not depend on how any module was produced.

The initial symbol policy should implement:

- Per-module local symbol namespaces.
- Strong global definitions.
- Weak definitions and deterministic strong-over-weak selection.
- Common symbols with maximum size/alignment rules.
- Duplicate strong-definition diagnostics.
- Undefined-reference diagnostics.
- An optional explicit import resolver expressed as pure symbol/address data for
  embedding and external execution tests.

The layout policy specifies:

- Base addresses or address-allocation constraints.
- Section grouping and ordering.
- Segment permissions: RX, R, RW, and zero-fill.
- Minimum and requested alignments.
- Entry symbol.
- Exported symbols visible to the host.
- Maximum image size and address-range limits.

The linker performs:

1. Symbol collection and preliminary resolution.
2. Section merging and segment assignment.
3. Common and BSS allocation.
4. Provisional fragment layout.
5. Instruction relaxation and range checking.
6. Re-layout until a stable encoding is reached.
7. Final symbol-address computation.
8. Load-address-dependent fixup application.

Alignment and relaxation can interact. Early implementations should favor
correctness through fixed-width targets, conservative encodings, and clear
out-of-range errors. Later shortening algorithms should be monotone or otherwise
have an explicit convergence guarantee. Branch veneers and literal islands are
target layout policies, not parser features.

## 9. In-memory image and portable binding contract

The primary output is a segmented logical image:

```ocaml
type permissions = {
  read : bool;
  write : bool;
  execute : bool;
}

type segment = {
  alignment : int;
  permissions : permissions;
  bytes : bytes;
  zero_fill : int;
}

type image = {
  segments : segment list;
  entry : address option;
  exports : (symbol * address) list;
}
```

`exports` are host-visible linker symbols, not debugger symbols.

Two loading modes are required:

- Fixed-address: addresses are supplied before final linking and all fixups are
  applied into an immediately usable image.
- Allocator-selected: the caller supplies a pure address-allocation result for
  segments subject to alignment/range constraints, after which the assembler
  applies final fixups and returns address-bound segment bytes.

The production API stops at address binding and materialization. It manipulates
ordinary pure-OCaml values and records intended R/W/X permissions as metadata; it
does not allocate native pages, change memory protection, flush instruction
caches, or call generated code. Consequently the same API works in a browser,
where target virtual addresses are layout values rather than JavaScript pointers.

Use a two-step portable contract:

1. `plan_image` returns segment sizes, alignments, range constraints, permissions,
   unresolved placement-dependent fixups, entry identity, and exports.
2. `bind_image` accepts explicit target addresses, validates all constraints,
   applies final fixups to pure byte buffers, preserves explicit zero-fill
   extents, and returns the final segmented image plus numeric entry/export
   addresses.

An embedding host that can execute the target ISA may consume this result using
its own secure write-then-execute implementation. Such an executor must allocate
writable memory, copy bytes, set final permissions, synchronize caches, and call
the entry point, but that functionality is outside the production OCaml packages
and communicates with tests through a serialized out-of-process protocol.

A flat byte-string serialization may be added for diagnostics or embedded-system
use, but it is not the canonical result because it cannot naturally express BSS,
permissions, alignment gaps, or independently placed segments.

## 10. CompCert compatibility

CompCert currently prints textual assembly and invokes an external assembler. The
new assembler should initially replace only that external step in test harnesses.
No change to CompCert is needed.

Later direct integration should translate CompCert values into the normalized or
lowered AST API. It must not make textual parsing semantically privileged: all
meaning required for simplification, lowering, linking, and image construction is
present in the public staged ASTs and validators.

Compatibility work must inventory, per target profile:

- All emitted instruction mnemonics and operand forms.
- Compiler-generated local label conventions.
- Section, alignment, data, visibility, common-symbol, and alias directives.
- Jump-table and literal-pool forms.
- Inline assembly behavior.
- Metadata-only directives that can safely be consumed and discarded.
- Runtime helper references.

Inline assembly means that complete compatibility eventually requires ordinary
assembler syntax beyond compiler-generated instructions. It should be supported
incrementally. CompCert's `extasm` regression intentionally emits fake `TEST...`
instructions and is a negative test rather than a valid encoding requirement.

The CompCert runtime is treated as ordinary assembly input. Required runtime `.S`
sources are preprocessed, assembled, and passed to the internal linker alongside
program inputs. They must not be invisibly built into the assembler.

## 11. Testing strategy

Testing has four distinct levels. A source need not be a freestanding executable
to be valuable at the first two levels.

### 11.1 Expect tests as the primary development tests

Expect-based tests are the main way to specify assembler behavior. Small `.s` or
`.c` inputs are checked into the repository together with human-readable expected
output. A Dune cram-style harness is appropriate for end-to-end command tests;
OCaml-level expect tests may additionally be used for parsers, expression
evaluation, and table generators. The exact framework can be selected during
bootstrapping, but the expected-output format must remain plain text and easy to
review.

Each capability test should expose the shortest useful trace. For example:

```text
$ asm --target x86_64 --fixed-base 0x1000 --dump-image return42.s
section .text address=0x1000 size=6 permissions=rx
00001000  b8 2a 00 00 00  ret42: mov eax, 42  [mov-r32-imm32]
00001005  c3                       ret          [ret-near]
export ret42 = 0x1000
```

The exact syntax should be finalized with the implementation. Important traits
are stable ordering, raw bytes, canonical disassembly, precise form identifiers,
and normalized symbols.

Expect suites should cover separate observable layers:

- Lexing and common parsing intermediates, especially dialect differences.
- Complete source AST construction, including target surface operands.
- Simplification/normalization, constant folding, aliases, and diagnostics.
- Lowering to fragments, symbols, relaxable forms, and fixups.
- Encoding plus internal disassembly.
- Multi-module symbol resolution and final layout.
- Multi-file link maps and image segments.
- Success and error diagnostics, including caret locations.
- Address-binding/image result and freestanding execution result.

Tests must also cover entry-path coherence:

- Text parse followed by simplification equals an equivalent directly constructed
  normalized AST.
- Lowering that normalized AST equals an equivalent directly constructed lowered
  module after validation.
- Textual and direct-AST paths produce the same linked image under the same layout
  policy.
- Malformed directly constructed ASTs fail at their public validation boundary
  instead of failing later in encoding or linking.

Constant-folding expectations must show both positive cases and deliberately
unevaluated cases involving symbols, current location, section-relative values,
and PC-relative fixups.

Every bug fix begins with the smallest failing expect test. Updates to expected
output must be reviewed as semantic changes, not accepted mechanically. Large
CompCert corpus tests should report concise summaries or focused diffs rather than
checking thousands of unstable lines into a single expectation.

The first cross-target ladder should compile equivalent minimal freestanding C
sources with each of the four CompCert configurations:

1. Exported function returning a constant.
2. Integer arguments and arithmetic.
3. Load/store of a global.
4. Conditional branch and loop.
5. Direct call within one file.
6. Call and data reference across two files.
7. Initialized data, BSS, alignment, and address constants.
8. A small result-block program with a callable entry point.

Each rung has x86-32, x86-64, ARM, and AArch64 expectations. A common feature is
considered implemented only when all four reach the relevant pipeline stage. If a
target requires a runtime helper, that helper is an explicit additional assembly
input and appears in the expected link map.

### 11.2 Corpus parsing and matching

Generate `.s` using the unmodified CompCert and parse every available translation
unit. The current test tree provides roughly:

| Suite | Approximate units | Primary value |
|---|---:|---|
| `regression` | 94 | Broad instruction, directive, and diagnostic coverage |
| `c` | 24 | Computational instruction coverage |
| `abi` | 6 generated files | Multi-file calls and ABI patterns |
| `compression` | 12 | Multi-file parser and symbol scale |
| `raytracer` | 14 | Numerical code and symbol scale |
| `spass` | 51 | Large real-world parser/linker workload |

This is approximately 201 normal assembly translation units before runtime and
platform-specific additions. Undefined external functions do not prevent a source
from being used for parser and instruction-matcher testing.

The PIC tests depend on shared objects, dynamic loading, and libc and are outside
the initial project scope.

### 11.3 Differential encoding and decoding

For each supported instruction form and representative compiled source:

- Assemble with this project.
- Assemble the same CompCert-emitted input with the target-prefixed GNU `as` in
  the test oracle. Use `--32` for x86-32 and `--64` for x86-64; the ARM fixture
  itself must select ARM rather than Thumb mode.
- Use the reference object only to recover section bytes, symbols, and relocation
  intent for comparison.
- Capture `readelf -SWsWr` and `objdump -dr` output before discarding the object,
  so section boundaries, symbol values, relocation kinds/addends, and canonical
  reference decoding are all reviewable.
- For relocation-free fixtures, extract the relevant section with the prefixed
  `objcopy --only-section=<section> -O binary` and require byte-for-byte equality.
- For fixtures containing relocations, never compare the unresolved placeholder
  bytes as if they were final encodings. Compare fixup kind, offset, symbol, and
  addend first, then compare final bytes only after both paths have been resolved
  at the same controlled addresses (for example with a minimal reference linker
  script).
- Compare fully resolved instruction bytes under a controlled layout.
- Decode the new assembler's output with both the internal diagnostic
  disassembler and an independent reference disassembler.
- Compare canonical instructions when byte equality is not meaningful because
  several legal encodings exist.
- Check semantic and exact-form encoder/decoder round-trip properties.
- Exercise invalid operands, missing features, and out-of-range immediates.

Object files in this level belong only to the external oracle. The product does
not gain an object reader or writer as a consequence.

The oracle hierarchy is explicit: GNU `as` establishes accepted syntax,
instruction bytes, and relocation intent; GNU `objdump` supplies an independent
canonical decode; the controlled reference link establishes final relocated
bytes; and QEMU or an optional matching external executor establishes behavior.
Agreement with only one level is not evidence for the levels after it.

### 11.4 Internal-link tests

Add small, purpose-built, multi-file assembly cases for:

- Local symbols with identical names in different inputs.
- Strong, weak, common, undefined, and duplicate symbols.
- Cross-file calls, branches, and data addresses.
- BSS and common allocation.
- Mixed section alignment and padding.
- Numeric local labels.
- Relaxable branches and deliberate out-of-range branches.
- Fixed-address and caller-address-selected binding.
- Import resolver success and failure.
- Segment permissions and zero-fill behavior.

The CompCert ABI generator is the best existing base for larger multi-file linker
tests, after adding a freestanding output mode.

### 11.5 Freestanding execution

The existing CompCert tests are mostly not directly executable without a host
runtime:

- The runnable regression tests generally use `printf`, `puts`, or `putchar`.
- The ABI harness uses stdio, string functions, `alarm`, and varargs helpers.
- The larger benchmark suites use allocation, file I/O, libc, or math functions.
- A set of regression translation units has no undefined symbols, but those are
  compile-only fragments rather than complete programs with an entry point.

Create a minimal test ABI instead of treating libc as part of the assembler:

- Entry receives an optional pointer to a result block.
- Test code writes expected/actual values or a failure code into memory.
- Entry returns a small pass/fail integer where the ABI permits it.
- No stdio, files, environment, allocation, or process services are assumed.

Initial execution tests should include:

- A freestanding mode for the CompCert ABI generator, removing `alarm`, stdio, and
  `strcmp` or replacing them with local routines.
- Pure computational kernels adapted to static buffers, such as Fibonacci, AES,
  SHA, or small numerical loops.
- Explicit runtime-helper inputs where a target needs CompCert helpers.

An import resolver may map output functions to host functions for broad native
smoke testing, but those results must be classified separately from freestanding
tests.

Execution testing uses QEMU user mode as the required development and CI backend
across all four targets. The four `qemu-*` user binaries and their target sysroots
are installed and have already executed system-linked CompCert smoke programs.
The four matching QEMU system emulators are also installed and verified, so
system mode is available as an independent secondary backend. User mode remains
the required M0/M1 path because its Linux process setup is simpler; system-mode
machine configuration, boot state, and control add substantial target-specific
work. GDB is installed and may drive or debug the system runner in batch mode. A
small project-external RSP client remains preferable for a minimal deterministic
CI protocol, but it is a design choice rather than a workaround for missing GDB.
An optional separately built, subprocess-isolated native executor may also test
executable-memory behavior when the host ISA and ABI match. No executor is an
OCaml library dependency or a requirement for using the browser-embeddable
assembler.

Environment snapshot (2026-08-07): `qemu-system-i386`,
`qemu-system-x86_64`, `qemu-system-arm`, and `qemu-system-aarch64` are installed
and report QEMU 10.0.11; GNU GDB 16.3 is installed at `/usr/bin/gdb`. This
verifies system-emulator and debugger availability separately from completion of
the per-target raw-image boot/control harnesses.

#### 11.5.1 Common test ABI and execution artifact

Every execution backend consumes the same logical image and test descriptor:

- Segment bytes, zero-fill sizes, alignments, and requested addresses.
- Entry address or exported entry symbol.
- Stack requirements.
- Address and size of a result block.
- Completion address or completion protocol.
- Execution timeout and optional instruction budget.

The result block is the architecture-neutral observation channel. It should have
a small versioned layout containing at least:

- Magic and ABI version.
- `not_started`, `running`, `passed`, `failed`, and `fault` status values.
- Test/case identifier and number of recorded values.
- Fixed-width expected and actual values or offsets to byte arrays.
- A bounded diagnostic payload.

The assembled test programs should not require stdout, libc, a filesystem,
debugger metadata, or target symbol-table formats. The external user-mode
transport may use its minimal syscall protocol solely to move the manifest,
segments, and result artifact. The host knows result and completion addresses
from the internal link map.

Every execution produces a deterministic host-side artifact suitable for an
expect test:

```text
backend      = qemu-aarch64-user
termination  = completed
entry        = 0x00401000
status       = passed
case         = add-global
values       = [42, 42]
```

On failure it should always contain the result block when recoverable and QEMU
stderr. A terminal PC, normalized register subset, or bounded instruction trace
is included only when the selected backend can capture it reliably. Host paths,
socket names, process IDs, and timing are removed before expect comparison.

#### 11.5.2 QEMU user-mode image runner (primary)

QEMU user mode executes a target-native Linux ELF rather than a raw image. Use a
small external transport helper to load the assembler's raw segments without
turning ELF production into an assembler feature. Segment files, the manifest,
and the helper ELF are test transport artifacts only.

The transport helper is not part of the production OCaml closure. To preserve the
project's no-C rule, it must not be implemented as C or linked with libc. Prefer
small checked-in target assembly helpers built by the reference GNU assembler and
linker, using only the direct Linux syscalls required by the protocol. An
externally supplied helper with recorded provenance is also acceptable. No
production or browser package may depend on the helper, GNU tools, QEMU, a
filesystem, or process APIs.

The user-mode protocol is:

1. The host oracle harness serializes each bound image segment plus a deterministic
   manifest containing requested address, initialized size, zero-fill size,
   alignment, permissions, entry, result-block location, and timeout.
2. It invokes the profile's installed `qemu-i386`, `qemu-x86_64`, `qemu-arm`, or
   `qemu-aarch64`, with the verified sysroot when the helper needs it.
3. The helper maps each segment writable at the requested guest virtual address,
   copies initialized bytes, clears zero-fill, and initializes the result block.
4. It changes each mapping to its final permissions, performs the target-required
   instruction-cache synchronization, and calls the entry through the target ABI.
5. It serializes the result block through its minimal syscall interface and exits.
6. The host enforces a wall-clock timeout, classifies normal exit, guest fault,
   signal, and timeout, and emits the normalized execution artifact.

The result block and manifest are explicit byte-level wire formats with fixed
offsets, widths, byte order, bounds, and versions. They must not depend on a C
structure layout, native OCaml value layout, pointer size, or host endianness.

Before running assembler-produced bytes, validate every helper and runner with
reference-assembled `return 42`, deliberate fault, and infinite-loop snippets.
Also induce a target-specific known-wrong encoding to prove that the behavioral
gate detects assembler failures. Pin QEMU/helper/tool versions and record the
exact helper hashes in test provenance.

This backend exercises real guest virtual-memory mappings and W-to-X transitions,
but it depends on the target Linux syscall ABI and QEMU's user-mode emulation. It
does not prove bare-metal startup, privilege state, or behavior without a guest
kernel ABI; the optional system-mode backend can provide that independent check.

#### 11.5.3 Optional external native executable-memory runner

The portable library's address-binding logic is fully testable without native
memory. A separate executable may additionally validate the behavior expected of
a native consumer:

1. Read a serialized image plan and choose addresses.
2. Return those addresses so the portable library can run `bind_image`.
3. Receive the final segments and allocate writable anonymous memory.
4. Copy bytes and zero-fill, then change pages to their final permissions.
5. Flush or synchronize the instruction cache as required.
6. Call the exported entry and return the result block over the protocol.

Never link this executor, an ABI-call stub, or an OS memory package into any
production OCaml library. The runner is supplied externally to the project as an
optional out-of-process testing tool; this repository does not ship C source for
it. Illegal instructions, memory faults, stack corruption, and infinite loops
remain isolated to the worker, and the shell/CI coordinator enforces the timeout.

This backend is enabled only when target ISA, execution mode, endianness, and ABI
match the helper process. It checks a consumer's memory protection, cache
synchronization, and ABI call behavior, but QEMU plus native/JavaScript byte
equality remain the required project gates.

#### 11.5.4 Optional QEMU system-mode bare-metal runner

The installed and verified QEMU system emulators may be used as an optional
second execution backend alongside the primary user-mode path. Their generic
loader can place raw segments at explicit physical addresses, and the GDB remote
stub can control execution and inspect the result block without debugger symbols:
<https://www.qemu.org/docs/master/system/generic-loader.html> and
<https://www.qemu.org/docs/master/system/gdb.html>.

The emulator binaries are no longer a provisioning blocker. A repeatable runner
still requires pinning machine/CPU/RAM maps and writing target boot shims that
establish x86 execution modes or ARM/AArch64 privilege and stack state. Control
may use installed GDB 16.3 in non-interactive batch mode, or a small external RSP
client for a narrower deterministic protocol. These are substantial independent
validation tasks and must not block initial assembler development. The system
runner consumes the same logical image, result-block wire format, and normalized
artifact as the user-mode runner.

### 11.6 JavaScript portability and dependency-purity gates

Browser-compatible architecture is a correctness requirement from the start, but
running a real browser harness is deferred until the image APIs and broader
assembler slices have stabilized. During M0/M1, Node.js is the required execution
environment for generated JavaScript. Every capability slice runs through the
same public API in three builds:

- Native OCaml, used for fast development tests.
- JavaScript emitted by js_of_ocaml.
- JavaScript emitted by Melange.

Environment status (2026-08-07): the cross-toolchain/CompCert installation is
verified, but this devcontainer does not yet expose either JavaScript compiler.
Provisioning pinned js_of_ocaml and Melange toolchains and passing the dependency
audit is therefore an explicit Milestone 0 task, not an already satisfied gate.

Given identical serialized inputs, all three must produce byte-identical image
segments and identical normalized AST, diagnostic, symbol, fixup, link-map, and
disassembly dumps. Tests must include 64-bit addresses and integers beyond the
JavaScript safe-integer range so an accidental conversion to `Number` fails
immediately. The Node harness supplies all fixture inputs as in-memory values and
must not grant the generated library implicit filesystem, subprocess, or
environment access. A later real-browser test reuses this in-memory harness.

The oracle workflow remains split cleanly:

1. A host shell/CI job runs CompCert, GNU tools, and QEMU and produces normalized
   fixture/oracle files.
2. Native and Node-run JavaScript builds consume those files as in-memory
   strings/bytes.
3. Neither JavaScript artifact tries to spawn a tool, read an implicit path, or
   access the host environment.

Add an automated production-closure audit that fails on C/assembly objects,
foreign-stub declarations, native-only modules, or a transitive package known to
compile C. Lockfiles alone are insufficient: the audit inspects the actual Dune
dependency/build graph for every library shipped to consumers. Test-only host
orchestration packages are reported separately and must not be reachable from a
production library.

## 12. Implementation roadmap

Milestones are capability-based rather than schedule estimates. x86-32, x86-64,
ARM, and AArch64 advance together through each milestone. No milestone means
"finish one architecture".

For each capability slice, use the same development loop:

1. Write the smallest freestanding C example expressing the capability.
2. Compile it to `.s` with each of the four unmodified CompCert configurations.
3. Assemble every emitted `.s` with its target-prefixed GNU `as`; retain the
   object's section, symbol, relocation, and disassembly oracle artifacts.
4. Add or update focused expect fixtures for the actual emitted syntax and GNU
   oracle result.
5. Implement only the missing common and target-specific behavior.
6. Compare relocation-free or identically resolved bytes and canonical
   disassembly with the target-prefixed GNU tools.
7. Once linking is available, construct and execute the image where a runner is
   available.

Handwritten assembly may isolate a corner case, but CompCert-generated assembly is
the primary driver for slice selection.

### Cross-compilation decision for Step 0

CompCert can be used as a cross compiler, but the practical model is one
separately configured and built `ccomp` per target architecture/profile, not one
universal `ccomp` that changes its verified back end at runtime.

The reasons are visible in the CompCert build:

- `configure` takes a mandatory target and supports `-toolprefix` for prefixed
  cross tools.
- The extracted OCaml build includes `$(ARCH)` in its source directories, so the
  selected architecture is compiled into that `ccomp` executable.
- The `-target`/`-conf` options select an `.ini` configuration for an already
  appropriate compiler; they should not be used to pair an x86-built executable
  with an ARM configuration.
- The supplied `setup-build` and `build-all` Makefile targets create separate
  linked source trees and configure/build several architectures in parallel.
- The supplied CI runner configures AArch64, ARM, PowerPC, and RISC-V builds with
  prefixed GNU cross toolchains.

The official installation manual confirms that cross-compilation is supported
and that a matching GCC/Diab cross compiler and cross libraries are required for
the complete preprocess/assemble/link workflow:
<https://compcert.org/man/manual002.html>.

The repository devcontainer is provisioned for the full workflow described in
`.ai/cross-plan.md`, so Step 0 uses real `.c -> .s -> .o -> executable` paths on
all four targets. Run:

```text
tools/compcert-cross-smoke.sh all
```

This builds and installs four target-specific CompCert executables under
`.cross-smoke-work/install/<target>/`, retains generated assembly under
`.cross-smoke-work/artifacts/<target>/`, checks the ELF machine, and runs every
linked executable with the corresponding QEMU user emulator and sysroot. Treat a
skip as a provisioning failure for this devcontainer, even though the reusable
script permits skips on host architectures for which Debian does not package a
particular cross toolchain.

The verified profile/tool matrix is:

| Fixture | CompCert profile and flags | External-tool prefix | Sysroot |
|---|---|---|---|
| x86-32 | `x86_32-linux` | `i686-linux-gnu-` | `/usr/i686-linux-gnu` |
| x86-64 | `x86_64-linux` | `x86_64-linux-gnu-` | `/usr/x86_64-linux-gnu` |
| ARM | `arm-linux`, `-marm` (ARMv7-A hard-float) | `arm-linux-gnueabihf-` | `/usr/arm-linux-gnueabihf` |
| AArch64 | `aarch64-linux` | `aarch64-linux-gnu-` | `/usr/aarch64-linux-gnu` |

Verification snapshot (2026-08-07): the smoke command built and installed four
separate CompCert 3.17 executables and completed all four compile/link/QEMU runs
with zero skips. `readelf` reported `Intel 80386`, `Advanced Micro Devices
X86-64`, `ARM`, and `AArch64` respectively. The retained CompCert-generated
`hello.s` files were also assembled directly by all four prefixed GNU assemblers
(GNU Binutils 2.44); each resulting object linked with its matching installed
`ccomp` and reproduced the expected output under QEMU. Oracle artifacts are under
`.cross-smoke-work/artifacts/<target>/gnu-oracle/`.

Fixture generation and differential testing must use the installed compiler for
the row, not `modules/CompCert/ccomp`, whose target depends on the last native
repository build. Preserve `Makefile.config`, `compcert.ini`, `ccomp -version`,
the `ccomp -S` command, and reference-tool versions with fixture provenance.

For each generated `.s`, invoke the matching prefixed GNU assembler directly as
the first oracle gate:

```text
i686-linux-gnu-as --32 -o fixture.o fixture.s
x86_64-linux-gnu-as --64 -o fixture.o fixture.s
arm-linux-gnueabihf-as -o fixture.o fixture.s
aarch64-linux-gnu-as -o fixture.o fixture.s
```

Then retain normalized `readelf -SWsWr fixture.o` and `objdump -dr fixture.o`
output. For a relocation-free `.text`, extract its bytes with the matching
`objcopy --only-section=.text -O binary fixture.o fixture.text.bin`. For symbolic
fixtures, compare relocation intent and resolve both implementations at identical
addresses before comparing final bytes.

The smallest bootstrap fixture may still use a preprocessed `.i` file containing
no headers:

```c
int asm_test_entry(void) { return 42; }
```

Then a target-specific `ccomp -S asm_test_entry.i` invokes neither the target
preprocessor, assembler, nor linker. This is useful for minimizing a code
generation test, but it is no longer a workaround for missing tools. The default
fixture path starts from `.c`, and its emitted `.s` must also pass the direct GNU
assembler oracle. A resource-constrained environment may build a lightweight
compiler with:

```text
./configure -no-runtime-lib -no-standard-headers \
  [-toolprefix <target-prefix>] <target-profile>
make light
./ccomp -S asm_test_entry.i -o asm_test_entry.s
```

Building CompCert itself still requires the documented host-side Rocq/Coq, OCaml,
Menhir, and GNU Make tools. A correct target profile is also required because ABI,
model, endianness, and system choices affect generated assembly. Always provide
the matching cross-tool prefix: configure probes the assembler and compiler
driver and records their capabilities in `compcert.ini`.

Pin the ARM execution mode explicitly (`-marm` initially) so fixture changes do
not accidentally switch to Thumb. Record all code-generation flags, including
optimization, PIC/PIE, floating-point, and debug settings. The first fixture
should use no debug generation and no PIC unless a later capability specifically
tests them.

The target GCC/binutils drivers, sysroot headers and libc, CompCert runtime
libraries, archivers, and QEMU user-mode execution paths are present now. Keep the
`.i -> .s` path as a fast, hermetic code-generation test, but do not let it replace
the full smoke test or direct-assembler oracle gate.

#### Fallback for an unprovisioned environment

The checked-in fixture bundle remains useful for consumers outside the
devcontainer, but it is not the primary Step 0 path here. If another environment
cannot build a target-specific compiler, acquire its assembly fixture from a
known-good unmodified CompCert build before implementing the parser or encoder.

Check in a bootstrap fixture bundle such as:

```text
fixtures/compcert-3.17/return42/source/asm_test_entry.i
fixtures/compcert-3.17/return42/x86_32-linux/asm_test_entry.s
fixtures/compcert-3.17/return42/x86_64-linux/asm_test_entry.s
fixtures/compcert-3.17/return42/armv7a-linux-hardfloat-arm/asm_test_entry.s
fixtures/compcert-3.17/return42/aarch64-linux/asm_test_entry.s
fixtures/compcert-3.17/return42/manifest.sexp
```

The manifest records:

- CompCert version, source revision, and executable hash when available.
- Exact configure target, `compcert.ini` architecture/model/ABI/endianness/system,
  and cross-tool prefix.
- Exact `ccomp` command and code-generation flags.
- Input and output hashes.
- Who or what environment generated the artifact.
- Whether the fixture was regenerated locally or imported from a trusted build.

Do not derive a missing target fixture by translating another architecture's
assembly or by using GCC/Clang output as a substitute. GCC/LLVM output is useful
as a byte oracle after parsing, but the textual compatibility fixture must be
actual CompCert output.

CI should have two modes:

- Always consume the checked-in bootstrap fixtures, making initial development
  independent of cross-compiler availability.
- In the provisioned devcontainer job, build all four CompCert configurations,
  regenerate the fixtures, run the direct GNU assembler oracles, and fail on a
  skip or unexplained difference. Regeneration changes require review because
  they may alter accepted syntax, relocations, or instruction coverage.

Relevant source locations in this checkout are `configure` (`-toolprefix` and
target profiles), `Makefile` (`setup-build`/`build-all`), `Makefile.extr`
(`$(ARCH)` in the extracted build), and `tools/runner.sh` (cross-tool prefixes).

### Initial end-to-end goal: `return 42` on four targets

The first externally meaningful deliverable is a walking skeleton through the
entire final architecture. For each of x86-32, x86-64, ARM, and AArch64:

```c
int asm_test_entry(void) { return 42; }
```

An unmodified CompCert produces the textual `.s` fixture. The project then:

1. Parses it into a complete source AST.
2. Simplifies it into a normalized semantic AST.
3. Lowers it into a module containing a `.text` fragment and exported symbol.
4. Encodes and internally disassembles the required instructions.
5. Builds one fixed-address RX image segment through `build_image`.
6. Loads that raw segment into the already validated QEMU executor environment.
7. Calls `asm_test_entry` through the target ABI.
8. Extracts a result block proving that the returned value is `42`.

The first slice intentionally does not support general multi-file linking, data
segments, unresolved symbols, arbitrary expressions, branch relaxation, imports,
or caller-selected placement. It supports only the directives and instruction
forms present in the four exact CompCert fixtures. Unsupported input fails
explicitly.

The restricted implementation must use the final phase types and public APIs. It
must not be a special `return42` encoder, concatenate bytes in the CLI, or bypass
the lowered-module/image-builder boundary. Later milestones expand accepted AST
values and policies without replacing this path.

The initial goal is complete only when all of the following evidence exists for
all four targets:

- Checked-in C and CompCert-generated assembly fixtures with reproducible
  generation commands and pinned target profiles.
- Successful direct assembly of each fixture with the matching prefixed GNU
  `as`, with the reference object, sections, symbols, relocations, and `objdump`
  decode retained as oracle artifacts.
- Reviewed expect output for source, normalized, and lowered ASTs.
- Reviewed fixed-layout map, raw bytes, form IDs, and both internal and GNU
  canonical disassembly.
- Exact byte agreement with the GNU assembler for relocation-free sections, or
  with the GNU reference link at the same addresses when relocations are present.
- Internal semantic and exact-form encode/decode round trips.
- QEMU artifact reporting `completed`, `passed`, and return value `42`.
- Equivalent images from text, directly constructed normalized AST, and directly
  constructed lowered AST inputs.
- Negative expectations for malformed syntax, wrong operand class, unsupported
  instruction/directive, invalid direct AST, and unresolved symbol.
- A production execution that invokes neither an external assembler nor an
  external linker; those tools appear only in fixture generation and the oracle.

### Verifiable bootstrap order

Implementation should approach that goal in the following order. Each checkpoint
is useful and testable even before the whole slice executes.

1. **Freeze profiles and fixtures.** Select exact CompCert configurations,
   assembly dialects, QEMU user binaries/sysroots, guest virtual load addresses,
   transport-helper ABIs, and reference tools. Check in the four minimal
   `.c`/`.s` pairs and document regeneration.

   Verification: regenerating a fixture either reproduces it or produces a
   reviewed, explicit difference. Tool versions and target profiles appear in a
   manifest.

2. **Validate the execution oracle independently.** Produce tiny known-good raw
   return-constant snippets with the reference toolchain. Load each through the
   QEMU user-mode runner and prove that the transport helper, guest mapping, ABI
   call, result block, fault/timeout classification, and normalization work before
   this assembler is involved.

   Verification: each golden snippet produces the expected deterministic QEMU
   artifact; a deliberately trapping and a deliberately looping snippet produce
   `fault` and `timeout` artifacts.

3. **Build phase skeletons and generic laws.** Define the three ASTs, origins,
   validators, phase functions, deterministic dumps, generic codec primitives,
   and restricted single-segment image builder. Use synthetic fixed- and
   variable-width ISAs for codec and phase tests.

   Verification: generic libraries test without linking a real target; malformed
   synthetic descriptions detect ambiguity, range, and inversion errors.

4. **Complete textual parsing only.** Parse each real fixture to a source AST,
   including target surface operands, but do not simplify during parsing.

   Verification: source-AST expects plus focused lexer/parser negative tests for
   each dialect.

5. **Complete simplification only.** Fold constants, normalize directives and
   expressions, remove metadata-only directives, and produce canonical semantic
   instructions.

   Verification: normalized-AST expects, constant-folding boundary cases,
   deliberately unevaluated symbolic expressions, validator failures, and direct
   normalized-AST coherence.

6. **Complete lowering and codecs.** Lower only the instruction forms needed by
   the fixtures into relaxable/exact fragments, then encode and decode them.

   Verification: lowered-AST expects, independent byte comparison, internal and
   reference disassembly, field boundary tests, and encode/decode properties.

7. **Complete the minimal image builder.** Resolve the one exported symbol, place
   one text section at a fixed address, reject unresolved symbols, encode bytes,
   and return the standard logical image.

   Verification: link-map/image expects, direct-lowered-AST coherence, segment
   bounds/invariant checks, and rejection of every unsupported link condition.

8. **Join the validated components.** Feed the generated image into the already
   validated QEMU runner and observe `42`.

   Verification: the four end-to-end artifacts plus an induced wrong-encoding
   test that demonstrates the execution gate detects failure.

### Evidence required for every later capability

Every improvement is delivered as a small capability slice with an evidence
bundle. The applicable items are mandatory:

- The smallest CompCert-generated or handwritten source exposing the capability.
- Source, normalized, and lowered AST expectations for every affected target.
- Positive, boundary, and negative diagnostics.
- Independent assembler/disassembler comparison for new binary forms.
- Internal semantic and exact-form round-trip properties.
- Link-map and image expectations for new symbol/layout behavior.
- QEMU execution when the capability has runtime semantics.
- Byte-identical output and diagnostics from native OCaml, js_of_ocaml, and
  Melange builds through the same in-memory public API.
- Optional external native-executor coverage when a capability changes the
  consumer-side permissions, cache, or ABI-call protocol and a matching helper is
  available; this is never a production-library dependency.
- Direct-AST/text path coherence when the feature is visible above lowering.
- A clean pure-OCaml production dependency audit.
- A concise update to the target/capability support matrix.

A feature is not complete merely because a corpus file parses or a generated byte
sequence looks plausible. It must pass the strongest applicable independent and
execution gates. Expectations must be reviewed rather than automatically
accepted.

CI should separate feedback latency without weakening the definition of done:

- Per commit: generic unit/property tests, focused expects, production-closure
  audit, js_of_ocaml and Melange compilation, Node.js smoke/equality tests, and the
  four minimal end-to-end slices where QEMU capacity permits.
- Per pull request: all four QEMU slices, differential encoding, native/js_of_ocaml/
  Melange output equality under Node, direct-path coherence, and affected corpus
  shards.
- Scheduled/full: complete corpus parsing, large multi-file applications, fuzzing,
  optional traces, resource/performance limits, and—after Milestone 4—a real-
  browser smoke/integration suite using the same in-memory JavaScript API. Run
  optional QEMU system-mode execution for every target whose boot/control harness
  has been validated.

### Independent extension axes and their gates

The assembler grows along several axes. A milestone should advance the smallest
number of axes necessary for its fixture; it should not broaden parser, ISA, and
linker scope simultaneously without separate evidence.

| Axis | Incremental progression | Verification gate for each increment |
|---|---|---|
| Semantic instruction coverage | return constant; arguments/arithmetic; stack/global memory; conditions/loops; calls; integer corner cases; floating/vector | Four-target AST expects, independent bytes/decode, operand boundaries, and QEMU result |
| Textual frontend | exact CompCert subset; more directives/expressions; aliases/pseudos; numeric labels; includes/macros/conditionals; broader handwritten syntax | Source-AST expects, malformed-input diagnostics, corpus acceptance delta, and unchanged direct-AST behavior |
| Simplification | literal folding; algebraic normalization; symbol-preserving forms; directive desugaring; target canonicalization | Normalized-AST expects, arbitrary-precision boundaries, non-folding cases, canonical/idempotence properties, and path coherence |
| Lowering/codec | exact forms; alternative forms; target fixups; variable length; literal pools/veneers | Lowered expects, ambiguity/reachability checks, encode/decode properties, reference comparison, and execution |
| Internal linking | one module/export; local/global; two files; weak/common; data/BSS; imports; duplicate/error policies | Deterministic link maps, reference-layout comparison where possible, negative symbol tests, mixed direct/text modules, and QEMU execution |
| Layout/relaxation | fixed text base; multiple sections; range selection; shortening; veneers/islands; rebasing | Two-address layout tests, convergence/invariant checks, boundary distances, final disassembly, and execution at each placement |
| Image binding/embedding | fixed raw image; multi-segment image; caller-selected virtual addresses; browser materialization; optional external native consumer | Segment/permission expects, identical native/JavaScript bytes, address-boundary tests, QEMU result blocks, and optional isolated consumer execution |
| Programmatic frontends | direct normalized fixtures; direct lowered fixtures; CompCert adapter; other generator APIs | Validator negatives and byte/image equivalence with a semantically identical textual path; no parser dependency in later libraries |
| Retargeting | four initial targets in lockstep; fuller profiles/features; RISC-V; PowerPC | Complete return-constant ladder first, then every capability gate through execution; no target dependency added to generic libraries |
| Description tooling | interpreted OCaml EDSL; generated tables; optional external `.isa` syntax | Same schema interpreted/generated equivalence, generator expects, ambiguity tests, reproducible output, and no loss of handwritten escape-hatch coverage |
| Scale and robustness | focused fixtures; regression corpus; ABI suite; multi-file applications; fuzzed syntax/bytes | Stable corpus summaries, bounded diagnostics, no crashes, reproducible images, memory/time budgets, and minimized regression cases |

The support matrix should record, for each target and capability, separate states
for parse, simplify, lower, encode, decode, link, js_of_ocaml, Melange, QEMU-user
execute, optional QEMU-system execute, and optional external-native execute. This
prevents a broad label such as "ARM supported" from hiding which stage or
deployment environment is actually complete.

- Adapt selected computational tests to the result-block ABI.
- Assemble needed CompCert runtime helpers as ordinary inputs.
- Generalize the already working QEMU user-mode path from one RX segment to
  multiple executable, read-only, writable, and zero-filled segments.
- Define the serialized external-executor protocol and optionally test it with a
  separately built subprocess on matching host profiles; do not link that helper
  into an OCaml package.
- Add bounded opt-in QEMU instruction traces for failed tests.
- Add expect tests showing segment maps, entry/export addresses, and normalized
  result-block contents.
- Require native/js_of_ocaml/Melange equality for every multi-segment image and
  run both generated JavaScript builds under Node through the in-memory API.

Exit criterion: the same representative CompCert-compiled, multi-file,
freestanding programs report correct results on x86-32, x86-64, ARM, and AArch64
without libc, object files, or a system linker. The portable library materializes
the same images in native OCaml and both browser toolchains with no C-backed
production dependency.

### Milestone 5: Expand CompCert coverage in parallel

- Add the deferred real-browser harness for the already validated in-memory API;
  run representative parser, encoder, linker, and multi-segment image fixtures
  without Node or POSIX polyfills.
- Grow instruction and directive coverage according to the four generated
  CompCert corpora, choosing small failures before large applications.
- Add relaxation, veneers, literal pools, and alternative encodings only when a
  focused fixture exposes the need.
- Keep the internal disassembler synchronized with every newly supported encoding
  form.
- Track handwritten codec escape hatches and require focused encoder, decoder,
  differential, and execution expectations for each.
- Review every proposed generic EDSL extension against the dependency and
  abstraction-promotion rules; add a target-independent synthetic test before
  accepting it.
- Add concise corpus-level expectations summarizing accepted files, unsupported
  forms, symbol dependencies, and differential mismatches.
- Generate and classify the broader CompCert assembly corpora for all four
  targets, using checked-in provenance manifests where CI cannot regenerate them.
- Progressively enable regression, ABI, and selected benchmark-derived tests on
  all four targets.

Exit criterion: the intended CompCert corpus subset has no unexplained parse,
match, encode, decode, link, or execution failures on any initial target.

### Milestone 6: Additional CompCert targets

Add RISC-V and PowerPC using the same vertical-slice ladder, beginning again with
the return-constant fixture and advancing through arithmetic, memory, control
flow, two-file linking, and freestanding execution. A new target does not weaken
the expect, differential, disassembly, or execution gates.

After the four initial targets have stabilized the typed codec representation,
decide whether to retain the OCaml EDSL as the authored format or add the compact
external `.isa` syntax that elaborates to it. This decision must be supported by
side-by-side descriptions from all four encoding families, not by one target.

### Milestone 7: Broader assembler language

- Add includes, conditional assembly, repetition, and user macros.
- Expand handwritten assembly compatibility beyond constructs emitted by
  CompCert.
- Improve shortest-encoding relaxation and branch-island policies.

### Milestone 8: Late CompCert integration

- Add an alternate frontend converting CompCert `Asm.program` values directly
  into the normalized AST where the assembler should retain pseudo/form decisions,
  or into the lowered AST where CompCert has already made them.
- Document which CompCert constructs map at each boundary and reject any construct
  whose semantics would be lost rather than falling back silently to text.
- Keep the textual frontend and differential tests as independent validation.
- Consider verified encoders, fixup application, and layout invariants only after
  the executable architecture is stable.

This integration must not introduce a separate linker or target model, and must
not invoke the textual parser internally.

## 13. Precedents and lessons

No single precedent supplies the complete desired design. The relevant systems
generate different subsets of parsers, encoders, decoders, printers, semantics,
and execution infrastructure:

| System | Generated or shared facilities | Lesson for this project |
|---|---|---|
| LLVM TableGen/MC | Operand matchers, code emitters, disassembler tables, assembly printers, pseudo lowering | Strongest production precedent for one record database feeding several specialized generators; handwritten target hooks remain necessary |
| New Jersey Machine-Code Toolkit/SLED | Symbolic encoders and decoders from compact instruction-representation specifications | Closest precedent for treating encoding/decoding as a bidirectional relation |
| GNU CGEN | Assembler, disassembler, and simulator generators from CPU descriptions | Demonstrates broad application-independent retargeting, though its Scheme tooling is older |
| QEMU decodetree | Decode trees and translator dispatch from bit patterns, fields, formats, and overlap groups | Good model for readable fixed-bit syntax and explicit ambiguity/priority rules; decoder-only |
| Ghidra SLEIGH | Instruction decoding, assembly display, decode context, and p-code semantics | Good model for tokens, fields, context, and constructors; oriented toward reverse engineering rather than encoding |
| Sail | Typed ISA semantics and bidirectional mappings between values and bit representations | Useful model for typed bitvectors and partial mappings; adopting its full semantics language would be excessive initially |
| DynASM | Runtime instruction emission, labels, and fixups | Confirms the in-memory generation use case, but is primarily encoder-oriented |
| GNU assembler internals | Fragments, fixups, and relaxation | Useful layout model even when equivalent concepts are never serialized into an object file |

LLVM uses separate TableGen backends for code emission, assembly matching,
printing, disassembly, and pseudo lowering. The project should copy this
separation while making the shared semantic/exact-form relation more explicit and
omitting object streamers and writers.

SLED is particularly close to the desired codec language: it was designed for
symbolic encoding and decoding and was used by assemblers, disassemblers, runtime
code generators, and a retargetable linker. SLEIGH descends from that work but
focuses on decode and semantic analysis.

QEMU decodetree's explicit overlap and no-overlap groups are worth adopting as
static checks in the codec generator. Sail's bidirectional mappings are a useful
model for small reversible relations such as register or width fields, without
requiring the project to adopt Sail's complete executable ISA semantics.

OCaml's module signatures and functors are the direct mechanism for expressing
associated target types and constructing reusable implementations. GADTs supply
runtime type representations and equality refinement inside the codec DSL; they
are complementary to modules rather than an alternative target-plugin system.

CompCertELF and later verified assembler projects demonstrate possible proof
boundaries around encoders and object construction. Their ELF production is not
an initial project requirement. The OCaml compiler itself primarily prints textual
assembly and delegates to a system assembler, so it is not a reusable retargetable
assembler implementation.

## 14. Definition of the initial successful system

The first complete version is successful when it can:

1. Consume the supported ordinary x86-32, x86-64, ARM, and AArch64 assembly
   emitted by unmodified CompCert configurations.
2. Consume several source files in one invocation.
3. Encode instructions and data without an external assembler.
4. Resolve all internal symbols and required CompCert runtime helpers without a
   system linker.
5. Produce RX, R, RW, and zero-filled segments directly in memory.
6. Return an entry address and explicitly selected exported addresses.
7. Execute a representative freestanding CompCert test corpus successfully.
8. Diagnose unsupported instructions, directives, unresolved symbols, duplicate
   definitions, and range failures precisely.
9. Do all of the above without producing object files and without constructing or
   retaining debugger or unwind information.
10. Provide reviewed expect tests for each pipeline layer and each supported
    capability on all four initial targets.
11. Decode every assembler-emitted instruction into a canonical diagnostic form,
    expose the selected encoding form, and pass semantic and exact-form round-trip
    tests.
12. Build the four target drivers through the same functor boundary while using
    typed GADT/codec schemas for instruction forms.
13. Run the common freestanding result-block tests under the four pinned QEMU
    user-mode profiles and extract deterministic artifacts through the versioned
    helper/result-block protocol.
14. Compile the complete production target registry with native OCaml,
    js_of_ocaml, and Melange and produce byte-identical images and normalized
    diagnostics through the same in-memory API.
15. Contain no C/assembly stubs or direct/transitive C-backed dependency in the
    production closure, as verified from the actual build graph.
16. Require no filesystem, process, Unix, native-pointer, or environment facility
    from the production API; run a smoke corpus in a real browser without Node
    polyfills.
17. Keep optional native executable-memory testing isolated behind a serialized
    subprocess protocol, with no executor or ABI-call stub linked into an OCaml
    package.
18. Keep the generic codec/EDSL, assembler core, and linker free of dependencies
    on concrete architectures, with automated dependency checks and synthetic-ISA
    tests enforcing the boundary.
19. Produce equivalent validated images from textual input and from direct
    normalized/lowered AST construction, without making the parser a dependency
    of later passes.
